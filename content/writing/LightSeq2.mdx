These notes examine **LightSeq2**, the training-focused successor to LightSeq. The system accelerates the complete Transformer training loop—forward, backward, parameter updates, and temporary-memory management—without changing the model's core mathematics.

> **Paper:** [_LightSeq2: Accelerated Training for Transformer-based Models on GPUs_](https://arxiv.org/abs/2110.05722)\
> **Repository:** [ByteDance LightSeq](https://github.com/bytedance/lightseq)\
> **Core idea:** Treat Transformer training as one GPU execution system, then remove overhead from computation, mixed-precision updates, and tensor lifetimes together.

The focus is to understand **why LightSeq2 is needed, how each optimization changes GPU execution, and where the idea appears in the implementation**.

---

## 1. Overview

### 1.1 Training Problem

LightSeq2 targets a systems problem: **Transformer training is expensive, and inference-oriented optimizations do not cover the full training loop**.

Training adds work that inference does not have:

```text
Forward
↓
Backward
↓
Gradient Synchronization
↓
Parameter Update
+
Activation / Gradient Storage
```

LightSeq2 keeps the Transformer algorithm unchanged and focuses on making this execution path more efficient on the GPU.

$$
\boxed{\text{Same training algorithm} \rightarrow \text{more efficient GPU execution}}
$$

### 1.2 Existing Limitations

Earlier systems often optimized only part of the problem:

- inference only,
- encoder-only training,
- or individual GPU operators.

A complete Transformer training system must also handle decoder computation, cross attention, criterion, backward propagation, optimizer updates, and training-time memory.

That is why LightSeq2 is designed as a **system-level training optimization**, rather than one isolated faster kernel.

### 1.3 Training Bottlenecks

The paper groups the main bottlenecks into three families:

These three bottlenecks determine the rest of the paper:

```text
Computation
→ Graph Optimization
→ Reduction Rewriting

Optimizer
→ Mixed-Precision Trainer

Memory
→ Memory Management
```

### 1.4 System Design

LightSeq2 uses four main techniques:

1. **Graph Optimization** — reduce fine-grained GPU execution overhead.
2. **Reduction Rewriting** — improve reduction-heavy operators such as LayerNorm and Softmax.
3. **Mixed-Precision Trainer** — reduce fragmented optimizer work and precision-conversion overhead.
4. **Memory Management** — reuse temporary storage according to tensor lifetime.

The rest of the notes follow this dependency order.

## 2. Graph Optimization

This chapter starts from one concrete question:

> A Transformer layer already uses fast GEMMs. Why can the layer still be slow?

The answer is that the large GEMMs are only part of the execution. Around them are many smaller operations that repeatedly launch kernels and move data through global memory.

We can follow one attention block to see the problem.

<a id="sec-gpu-overhead"></a>
### 2.1 GPU Overhead

Suppose an attention output projection produces a tensor \(X\), and the next operations are:

```text
X
↓
Bias Add
↓
Dropout
↓
Residual Add
```

Mathematically, these operations are cheap.

But a generic framework may execute them as three separate GPU kernels:

```text
X
↓
Bias Add Kernel
↓
write X + b to global memory

↓
Dropout Kernel
↓
read X + b
↓
write dropped tensor

↓
Residual Kernel
↓
read dropped tensor
↓
write final output
```

The GPU therefore pays for:

```text
kernel launch
+
global-memory write
+
global-memory read
```

multiple times, even though the arithmetic itself is simple.

This is the central motivation for Graph Optimization:

$$
\boxed{\text{Low FLOPs} \neq \text{Low GPU cost}}
$$

The next question is therefore: **which operations are already efficient, and which ones should LightSeq2 optimize?**

<a id="sec-gemm-nongemm"></a>
### 2.2 GEMM vs. Non-GEMM

Consider the QKV projection:

$$
[Q,K,V]=XW_{QKV}
$$

If:

```text
batch = 32
sequence length = 512
hidden size = 768
```

then the projection is a large matrix multiplication. cuBLAS is already highly optimized for this kind of work.

So LightSeq2 does **not** try to replace it.

Immediately after the GEMM, however, the output still needs:

```text
add Q/K/V bias
↓
split Q, K, V
↓
reshape into heads
↓
rearrange memory layout
```

These operations are smaller and more memory-oriented.

This gives LightSeq2 a simple rule:

```text
Large matrix multiplication
→ keep cuBLAS

Small surrounding operations
→ custom Transformer-specific CUDA kernels
```

> **Code:** [Appendix C — GEMM/non-GEMM boundaries](#appendix-encoder-fusion)

This classification leads directly to operation fusion: if several non-GEMM operations touch the same data, can they be executed together?

<a id="sec-operation-fusion"></a>
### 2.3 Operation Fusion

Return to the attention-output example:

```text
Bias Add
↓
Dropout
↓
Residual Add
```

Suppose one element has:

```text
projection output = 2.0
bias              = 0.5
residual          = 1.0
dropout keeps it
```

Mathematically:

```text
2.0 + 0.5
= 2.5
↓
apply dropout scaling
↓
+ 1.0 residual
```

LightSeq2 does not change this result.

It changes **where the intermediate value lives**.

Without fusion:

```text
2.0 + 0.5
↓
write 2.5 to global memory
↓
read 2.5 again
↓
dropout
↓
write again
↓
read again
↓
add residual
```

With fusion:

```text
load projection value
↓
add bias
↓
apply dropout
↓
add residual
↓
store final result
```

The intermediate value can remain in registers instead of being materialized repeatedly in global memory.

So fusion changes the execution boundary:

$$
\boxed{\text{Fusion reduces memory traffic and launches, not mathematical FLOPs}}
$$

> **Code:** [Appendix C — fused bias/dropout/residual](#appendix-encoder-fusion)

The same idea appears earlier in the attention path, immediately after the QKV GEMM.

<a id="sec-qkv-transform"></a>
#### QKV Transform

Suppose:

```text
batch size = 2
sequence length = 4
hidden size = 8
number of heads = 2
head dimension = 4
```

The QKV projection produces:

```text
[batch, sequence, 3 × hidden]
= [2, 4, 24]
```

But attention wants Q, K, and V organized by head:

```text
Q → [2, 2, 4, 4]
K → [2, 2, 4, 4]
V → [2, 2, 4, 4]
```

A naive execution could do:

```text
QKV GEMM result
↓
Bias Add Kernel
↓
temporary tensor
↓
Split / Reshape Kernel
↓
Head-layout tensor
```

LightSeq2 instead combines the work:

```text
read projected element
↓
add Q/K/V bias
↓
determine head + dimension
↓
write directly to final attention layout
```

So fusion is not limited to arithmetic.

It can combine:

$$
\boxed{\text{Computation} + \text{Data Movement}}
$$

> **Code:** [Appendix C — QKV bias/layout transform](#appendix-encoder-fusion)

At this point, the optimized encoder path becomes easier to read as one execution story:

<a id="sec-encoder-execution"></a>
#### Encoder Execution

```text
LayerNorm
↓
QKV GEMM                  ← cuBLAS
↓
Bias + Layout Transform   ← custom CUDA
↓
QKᵀ GEMM                  ← cuBLAS
↓
Softmax                   ← custom CUDA
↓
Dropout
↓
SV GEMM                   ← cuBLAS
↓
Layout Transform
↓
Output GEMM               ← cuBLAS
↓
Bias + Dropout + Residual ← fused CUDA
```

The important pattern is:

```text
optimized GEMM
↓
custom non-GEMM work
↓
optimized GEMM
↓
custom non-GEMM work
```

> **Code:** [Appendix A — Python layer](#appendix-python-layer) · [Appendix B — extension bridge](#appendix-extension-bridge) · [Appendix C — encoder execution](#appendix-encoder-fusion)

Graph Optimization is therefore not “replace Transformer with custom CUDA.” It is “keep strong GEMM implementations and remove waste around them.”

The same philosophy appears in a few special Transformer components.

<a id="sec-embedding-backward"></a>
### 2.4 Embedding Backward

Suppose the input sequence is:

```text
["the", "cat", "the"]
```

and `"the"` has token id 5.

During backward:

```text
position 0 → gradient contribution g₀ to E[5]
position 2 → gradient contribution g₂ to E[5]
```

The final gradient must be:

$$
\nabla E_5 = g_0 + g_2
$$

Now imagine two GPU threads processing those two positions at the same time.

Without synchronization:

```text
thread 0 reads E[5]
thread 2 reads E[5]
↓
both update independently
↓
one write may overwrite the other
```

LightSeq2 uses atomic accumulation:

```text
thread 0 ─┐
          ├→ atomicAdd(E[5])
thread 2 ─┘
```

so both contributions survive.

The paper expresses the same idea as:

$$
\nabla E_w
=
s\sum_{i:x_i=w}
m(i)\odot\nabla y^{(x_i,i)}
$$

The important systems point is that embedding backward is **many-to-one aggregation**, so it needs a kernel designed around that access pattern.

> **Code:** [Appendix D — embedding backward and atomic accumulation](#appendix-embedding)

<a id="sec-criterion"></a>
### 2.5 Criterion

At the other end of the model, consider a vocabulary with four tokens:

```text
[A, B, C, D]
```

Suppose the correct token is `C`.

Without label smoothing, the target is:

```text
[0, 0, 1, 0]
```

With label smoothing, a small amount of probability mass is distributed to all vocabulary entries.

If Softmax produces:

```text
q = [0.1, 0.2, 0.6, 0.1]
```

then each logit gradient is essentially:

```text
predicted probability
−
smoothed target probability
```

The paper derives:

$$
\nabla h_i=
\begin{cases}
q_i-\frac{\alpha}{V}-1+\alpha, & i=k\\[4pt]
q_i-\frac{\alpha}{V}, & i\neq k
\end{cases}
$$

Once the shared Softmax normalization is known, each vocabulary position can finish its gradient independently.

So the implementation becomes:

```text
shared Softmax statistics
↓
many independent vocabulary threads
↓
final gradient
```

rather than explicitly materializing a full Softmax Jacobian.

> **Code:** [Appendix E — label-smoothed cross entropy](#appendix-criterion)

<a id="sec-layer-batched-cross-attention"></a>
### 2.6 Layer-Batched Cross Attention

Now consider an encoder-decoder Transformer with three decoder layers.

Each decoder layer needs K/V projections from the same encoder output:

```text
encoder output
├─ decoder 0 K/V GEMM
├─ decoder 1 K/V GEMM
└─ decoder 2 K/V GEMM
```

This means three separate, relatively smaller GEMMs.

LightSeq2 stacks the three K/V weight sets:

```text
[W₀
 W₁
 W₂]
```

and computes one larger projection:

```text
encoder output
↓
one large K/V GEMM
↓
large stacked result
↓
split into decoder 0 / 1 / 2
```

Formally:

$$
[y^{key};y^{value}]
=
[W^{key};W^{value}]x+[b^{key};b^{value}]
$$

The amount of mathematical work is similar, but the execution is more GPU-friendly because one larger GEMM exposes more parallelism and reduces repeated launch overhead.

> **Code:** [Appendix F — layer-batched K/V projection](#appendix-cross-attention)

Graph Optimization has now handled fine-grained execution and special Transformer dataflow patterns.

But one important class of operations does not fit the same fusion story: **reductions**. LayerNorm and Softmax require many threads to cooperate on a shared statistic.

That leads to the next chapter.

## 3. Reduction Rewriting

The key difference is:

```text
Element-wise operation
→ each output can be computed independently

Reduction
→ many inputs cooperate to produce one shared value
```

So LightSeq2 cannot solve LayerNorm and Softmax simply by “fusing more.”

<a id="sec-layernorm-forward"></a>
### 3.1 LayerNorm

Take a tiny vector:

$$
x=[1,3]
$$

Its mean is:

$$
\mu(x)=2
$$

A conventional variance calculation follows:

```text
compute mean = 2
↓
compute
[(1-2)² + (3-2)²] / 2
↓
variance = 1
```

The second step depends on the first.

LightSeq2 rewrites variance as:

$$
\operatorname{Var}(x)
=
E[x^2]-E[x]^2
$$

For the same vector:

$$
E[x^2]
=
\frac{1^2+3^2}{2}
=
5
$$

so:

$$
5-2^2=1
$$

The mathematical result is the same.

But the GPU execution changes from:

```text
sum(x)
↓
mean
↓
sum((x - mean)²)
```

to:

```text
input x
├─ sum(x)
└─ sum(x²)
↓
mean + variance
```

Now `sum(x)` and `sum(x²)` can be accumulated together.

That is why the rewrite matters: **it removes a reduction dependency**.

> **Code:** [Appendix G — LayerNorm forward](#appendix-layernorm)

<a id="sec-layernorm-backward"></a>
#### Backward

Suppose one LayerNorm row has four elements.

A naive mental model is:

```text
gradient for x₀ depends on all outputs
gradient for x₁ depends on all outputs
gradient for x₂ depends on all outputs
gradient for x₃ depends on all outputs
```

That looks difficult to parallelize.

The paper rearranges the derivative so the shared information becomes two reductions:

$$
A=\sum_j w_j\nabla y_j
$$

$$
B=\sum_j w_j\nabla y_jx_j
$$

Then each element uses:

```text
its own local values
+
shared A
+
shared B
↓
final ∇x_i
```

So the GPU structure becomes:

```text
reduce A and B
↓
broadcast shared results
↓
many independent element-wise finishes
```

Again, the important idea is not “less math.”

It is **better dependency structure**.

> **Code:** [Appendix G — LayerNorm backward](#appendix-layernorm)

<a id="sec-softmax"></a>
### 3.2 Softmax

Softmax has a different reduction dependency.

Suppose attention scores are:

$$
[1000,\ 1001,\ 999]
$$

Directly computing:

$$
e^{1001}
$$

can overflow.

Stable Softmax first finds:

$$
\max(x)=1001
$$

then subtracts it:

```text
[1000, 1001, 999]
↓
[-1, 0, -2]
```

and computes:

$$
[e^{-1}, e^0, e^{-2}]
$$

before the sum reduction.

So the execution is:

```text
max reduction
↓
subtract max
↓
exp
↓
sum reduction
↓
normalize
```

Unlike LayerNorm, the second reduction genuinely depends on the first.

LightSeq2 therefore optimizes **the reduction schedule** rather than removing the dependency.

Now consider two sequence lengths:

```text
L = 32
L = 1024
```

A kernel designed for 1024 elements would waste many threads on a 32-element row. A kernel designed for 32 elements would not expose enough parallelism for 1024.

So LightSeq2 uses different launch configurations depending on the reduction shape.

```text
short sequence
→ compact reduction configuration

long sequence
→ more threads / different reduction schedule
```

> **Code:** [Appendix H — stable Softmax and shape-dependent dispatch](#appendix-softmax)

Graph Optimization and Reduction Rewriting together optimize **model computation**.

After backward finishes, however, gradients still have to update the model parameters.

That is the next bottleneck.

## 4. Mixed-Precision Trainer

<a id="sec-baseline-update"></a>
### 4.1 Baseline Update

Suppose an FP16 parameter is approximately:

```text
w = 1.000
```

and the optimizer wants to apply:

```text
Δw = 0.0001
```

Around that magnitude, FP16 may not preserve such a small change accurately enough.

So mixed-precision training usually performs optimizer arithmetic in FP32.

A conventional update therefore looks like:

```text
FP16 parameter / gradient
↓
convert or copy to FP32
↓
optimizer update
↓
convert result back to FP16
```

Now scale this to millions or billions of parameters.

The arithmetic in Adam or SGD is not necessarily the only bottleneck. The system repeatedly moves and converts parameter data.

The second problem is fragmentation: a model may have many separate parameter tensors, each requiring its own update work.

So the optimizer bottleneck is:

```text
many small parameter tensors
+
FP16 ↔ FP32 memory movement
```

<a id="sec-symbolic-linking"></a>
### 4.2 Symbolic Tensor Linking

Suppose a model has three parameter tensors:

```text
p1 = 100 elements
p2 = 200 elements
p3 = 50 elements
```

A fragmented representation is:

```text
p1        p2             p3
[100]     [200]          [50]
```

LightSeq2's paper design instead prefers one continuous workspace:

```text
|---- p1 ----|-------- p2 --------|-- p3 --|
0           100                   300      350
```

Each logical parameter can now be represented by:

```text
start offset
+
length
```

The optimizer can traverse one continuous region instead of managing many small independent update targets.

That is the intuition behind **symbolic tensor linking**.

> **Code:** [Appendix A — flat parameter layout](#appendix-python-layer) · [Appendix I — trainer implementation](#appendix-trainer)

<a id="sec-on-the-fly"></a>
### 4.3 On-the-Fly Conversion

A conventional mixed-precision design may keep:

```text
FP16 model parameter
+
FP32 master parameter
```

for the entire model.

LightSeq2's paper design instead tries to keep high precision only where the arithmetic is happening.

For one parameter element:

```text
FP16 value in global memory
↓
load into register
↓
convert to FP32
↓
apply Adam / SGD update
↓
convert updated value back to FP16
↓
store
```

The FP32 value exists only temporarily in the register.

So the principle is:

$$
\boxed{\text{FP16 storage} \rightarrow \text{FP32 arithmetic} \rightarrow \text{FP16 storage}}
$$

This reduces the need for a full model-sized FP32 storage copy.

> **Code:** [Appendix I — current LSAdam path](#appendix-trainer)

## 5. Memory Management

Training stores many temporary tensors because backward needs information from earlier forward operations.

The important question is not:

> How many temporary tensors exist?

It is:

> How many are alive at the same time?

<a id="sec-memory-types"></a>
### 5.1 Memory Types

LightSeq2 separates memory conceptually into:

**Permanent**

- parameters,
- gradients,
- optimizer state.

**Temporary**

- attention intermediates,
- layout-transform buffers,
- reduction buffers,
- backward intermediates.

Only temporary storage can be aggressively reused.

<a id="sec-tensor-lifetime"></a>
### 5.2 Tensor Lifetime

Suppose attention backward needs three logical buffers:

```text
A = ∇context
B = ∇softmax
C = ∇QKV
```

and their lifetimes are:

```text
time →

A: █████
B:      ████
C:          █████
```

A and C never overlap.

A naive allocator might reserve:

```text
memory for A
+
memory for B
+
memory for C
```

But LightSeq2 can reuse:

```text
physical block 1 → A first, then C
physical block 2 → B
```

So three logical tensors only require two physical blocks.

This is the core memory-management idea:

$$
\boxed{\text{Logical tensor count} \neq \text{physical buffer count}}
$$

<a id="sec-attention-backward"></a>
### 5.3 Attention Backward

The same idea appears in self-attention backward.

A simplified sequence is:

```text
1. compute ∇V and ∇Softmax
2. finish Softmax backward
3. compute ∇Q and ∇K
4. transform Q/K/V gradients
5. run QKV projection backward
```

Once step 2 finishes, the temporary Softmax-gradient buffer is dead.

That memory can be reused by a later tensor.

So the buffer manager follows the execution timeline:

```text
tensor needed
→ assign shared region

tensor consumed
→ region becomes reusable

later tensor
→ reuse same region
```

The paper's example reduces temporary storage from approximately:

$$
9BLH + BL^2N
$$

to:

$$
3BLH+\max(3BLH,BL^2N)
$$

The exact formula is less important than the principle:

$$
\boxed{\text{Peak memory} = \text{maximum simultaneously-live storage}}
$$

> **Code:** [Appendix J — attention-backward buffer aliases](#appendix-memory)

<a id="sec-preallocation"></a>
### 5.4 Preallocation

Now suppose three batches require:

```text
batch 1 → 400 MB
batch 2 → 650 MB
batch 3 → 500 MB
```

A dynamic allocator may repeatedly resize or allocate/free buffers as the workload changes.

LightSeq2 instead reserves the maximum required workspace:

```text
workspace = 650 MB
```

and reuses it:

```text
batch 1 → use first 400 MB
batch 2 → use all 650 MB
batch 3 → use first 500 MB
```

So the hot training loop avoids repeated allocation calls.

```text
estimate maximum need
↓
allocate once
↓
reuse every iteration
```

> **Code:** [Appendix J — shared workspace and backward orchestration](#appendix-memory)

## 6. Software Architecture

LightSeq2 uses a simple layered stack:

<Mermaid

    d["GPU"]
    a --> b --> c --> d`}
  caption="LightSeq2 software stack"

Suppose a PyTorch model executes:

```text
encoder(x)
```

The call moves through:

```text
LSTransformerEncoderLayer
↓
custom autograd Function
↓
PyBind
↓
TransformerEncoderLayer::Forward
↓
cuBLAS + custom CUDA kernels
```

The abstraction changes at each level:

```text
Python model object
→ PyTorch tensor operation
→ C++ raw GPU pointers
→ GPU execution
```

That is the architectural point: **keep a convenient framework API while moving execution control into C++/CUDA**.

## 7. Experiments

The experiments answer three practical questions:

```text
Does the whole system get faster?
↓
Do the individual optimizations matter?
↓
Does memory usage improve?
```

### 7.1 Overall Speedup

Across Transformer, ViT, BERT, and GPT-2, LightSeq2 consistently outperforms the tested baselines.

For full encoder-decoder Transformer training, the paper reports roughly:

- **1.4–2.8×** speedup on V100,
- **1.5–3.5×** speedup on A100,

depending on model size and batch-token configuration.

The important result is not one maximum number. It is that the system works across encoder-only, decoder-only, encoder-decoder, and vision Transformer workloads.

### 7.2 Optimization Breakdown

To understand why the full system is faster, imagine a training profile:

```text
40% GEMM
30% non-GEMM kernels
20% optimizer
10% communication
```

If kernel fusion cuts the non-GEMM portion and the trainer cuts optimizer time, the total runtime can improve substantially.

But with a larger batch, the profile may shift toward:

```text
70% GEMM
10% non-GEMM
10% optimizer
10% communication
```

Now there is less overhead left for LightSeq2 to remove.

This explains the paper's observation that relative speedup can shrink when large GEMMs dominate.

The operator benchmarks for LayerNorm, Softmax, Adam, and SGD support the individual mechanisms described earlier.

### 7.3 Memory and Scalability

In the reported Transformer experiments, LightSeq2 uses about **6 GB less GPU memory** than Fairseq for both Transformer-Base and Transformer-Big configurations.

Its memory footprint is also more stable because temporary workspace is allocated and reused.

Distributed scaling remains positive, but relative speedup decreases as synchronization occupies a larger fraction of runtime.

That limitation is expected: LightSeq2 mainly optimizes local computation and memory, not all-reduce communication.

---

## 8. Scope

LightSeq2 is a **systems optimization**, not a new Transformer algorithm.

It does not:

- replace self-attention with an approximation,
- change the model objective for speed,
- or turn the entire Transformer into one giant CUDA kernel.

Instead, it keeps the same training computation while changing:

```text
kernel boundaries
+
reduction schedule
+
mixed-precision update path
+
temporary-memory layout
```

#### A.1 Extension Loading and Autograd Dispatch

[Open the exact code: `transformer_encoder_layer.py` lines 21–79](https://github.com/bytedance/lightseq/blob/master/lightseq/training/ops/pytorch/transformer_encoder_layer.py#L21-L79)

This block is the Python-side control boundary.

**What happens:**

1. `TransformerBuilder().load()` loads the compiled LightSeq extension into Python.
2. `LSTransformerEncoderFunc` subclasses `torch.autograd.Function`, so PyTorch still sees one differentiable operation.
3. In `forward`, LightSeq chooses the FP16 or FP32 compiled entry point from the configuration.
4. The input and padding mask are converted to half precision when FP16 mode is enabled.
5. The compiled extension receives the layer id, input, mask, training mode, pre/post-LayerNorm mode, and quantization mode.
6. PyTorch saves the tensors required for backward in `ctx`.
7. In `backward`, LightSeq dispatches to the matching compiled backward entry point.
8. The C++/CUDA layer computes the input gradient, while the parameter gradient is retrieved from the layer-specific gradient buffer.

**Why this matters:**

PyTorch keeps responsibility for the outer autograd graph, but the internal Transformer layer is no longer decomposed into many ordinary PyTorch operators. That larger execution boundary gives LightSeq enough control to fuse operations and manage temporary memory itself.

#### A.2 Flat Parameter Layout

[Open the exact code: parameter allocation and offsets, lines 111–160](https://github.com/bytedance/lightseq/blob/master/lightseq/training/ops/pytorch/transformer_encoder_layer.py#L111-L160)

This block explains why the Python wrapper owns one flat `nn.Parameter` instead of many independent tensors.

**Walkthrough:**

- `gen_offset()` lists the sizes of every logical parameter region: QKV weights, QKV bias, attention output parameters, LayerNorm parameters, FFN parameters, and quantization metadata.
- `calc_offset()` turns those sizes into cumulative offsets.
- One flat parameter buffer is created using the final offset.
- `_get_weights(i)` later returns a view into the correct slice.

Conceptually:

```text
one flat parameter
| QKV W | QKV b | Attn W | Attn b | LN | FFN1 | FFN2 | ... |
          ↑
          logical tensors are slices, not separate allocations
```

This is useful for contiguous memory access and is closely related to the paper's preference for symbolic/contiguous parameter storage. It is **not identical** to the paper's whole-trainer symbolic-linking design, but it uses the same systems principle.

#### A.3 User-Facing Forward

[Open the exact code: `forward`, lines 286–325](https://github.com/bytedance/lightseq/blob/master/lightseq/training/ops/pytorch/transformer_encoder_layer.py#L286-L325)

This is what happens when a normal PyTorch model calls the LightSeq layer.

**Walkthrough:**

1. The wrapper records whether the module is in training mode and whether gradients are enabled.
2. Input tensors are made contiguous because the C++ side expects contiguous GPU memory.
3. The padding mask is converted to the large-negative additive form expected by attention.
4. If the public parameter is FP32 but execution uses FP16, a half-precision execution copy is prepared.
5. The parameter-gradient buffer is linked/assigned.
6. Batch-token and sequence-length bounds are validated.
7. The wrapper finally invokes `LSTransformerEncoderFunc.apply(...)`.

That final call crosses from ordinary PyTorch model code into LightSeq's custom autograd path.

#### B.1 Extension Build

#### B.2 PyBind Forward Boundary

[Open the exact code: `transformer_encoder_layer_fw`, lines 51–70](https://github.com/bytedance/lightseq/blob/master/lightseq/csrc/pybind/pybind_layer.cpp#L51-L70)

<a id="appendix-encoder-fusion"></a>
### C. Encoder Execution and Fusion

**Relevant reading:** [Section 2.2](#sec-gemm-nongemm) · [Section 2.3](#sec-operation-fusion) · [Section 2.4](#sec-qkv-transform) · [Section 2.5](#sec-encoder-execution) · [Section 6.3](#sec-encoder-forward)

#### C.1 Attention Forward

[Open the exact code: `attn_layer_fw`, lines 64–172](https://github.com/bytedance/lightseq/blob/master/lightseq/csrc/layers/transformer_encoder_layer.cpp#L64-L172)

This function is the clearest code representation of the paper's optimized Transformer graph.

Read it in five stages:

**Stage 1 — QKV preparation**

- Optional pre-LayerNorm runs first.
- `_qkv_linear.Forward(...)` performs the QKV projection through the matrix-multiplication wrapper.
- The projection output is then passed through the fused QKV bias/layout transformation.

This is the first important GEMM/non-GEMM boundary:

```text
cuBLAS GEMM
↓
LightSeq transform kernel
```

**Stage 2 — Attention scores**

The transformed Q and K buffers are passed to `_attn_scores.Forward(...)`, which performs the batched \(QK^\top\) matrix multiplication.

**Stage 3 — Softmax and attention dropout**

The score tensor goes through the LightSeq Softmax operator and then through attention-probability dropout.

These are non-GEMM stages implemented with custom kernels.

**Stage 4 — Context and output projection**

The probability matrix and V are multiplied to produce the context. The context is transformed back from the head-oriented layout, then the output projection runs as another GEMM.

**Stage 5 — Fused postprocessing**

The output projection is not followed by three independent framework operations. The `Dropout` operator's fused postprocessing path handles bias, dropout, and residual addition together.

This function therefore alternates:

```text
GEMM
→ custom non-GEMM
→ GEMM
→ custom non-GEMM
→ GEMM
→ custom non-GEMM
```

That is exactly the execution pattern described in the paper.

#### C.2 QKV Bias and Layout Fusion

[Open the exact QKV call, lines 108–112](https://github.com/bytedance/lightseq/blob/master/lightseq/csrc/layers/transformer_encoder_layer.cpp#L108-L112)

The QKV projection initially produces a dense matrix whose last dimension contains the three projected tensors. Attention, however, wants head-oriented Q/K/V buffers.

The transform call performs two jobs in one GPU stage:

1. add the learned QKV bias;
2. rearrange the projected data into the layout used by multi-head attention.

Why fuse these jobs?

Both operations touch the same projected elements. Performing them separately would require an extra kernel launch and another global-memory read/write pass.

#### C.3 Bias + Dropout + Residual

[Open the `Dropout` wrapper, lines 42–54](https://github.com/bytedance/lightseq/blob/master/lightseq/csrc/ops/includes/dropout.h#L42-L54)

[Open the fused CUDA kernel, lines 352–501](https://github.com/bytedance/lightseq/blob/master/lightseq/csrc/kernels/cuda/dropout_kernels.cu#L352-L501)

The wrapper maps the higher-level `bias_dropout_residual` operation to one CUDA launcher. The kernel then performs all three operations while the input values are already in registers.

**Kernel logic:**

1. A thread determines which vectorized input chunk it owns.
2. A random dropout mask is generated.
3. The bias index is derived from the hidden dimension.
4. Input, bias, and residual values are loaded.
5. The kernel computes the equivalent of:

```text
(input + bias)
↓
dropout + dropout scaling
↓
+ residual
```

6. Only the final result is written to output memory.
7. The dropout mask is stored because backward needs to know which activations were kept.

The optimization is not fewer mathematical operations. It is fewer trips through global memory and fewer kernel launches.

#### C.4 FFN Fusion

[Open the FP16/FP32 FFN path, lines 233–252](https://github.com/bytedance/lightseq/blob/master/lightseq/csrc/layers/transformer_encoder_layer.cpp#L233-L252)

The FFN path follows the same design philosophy:

```text
FFN GEMM 1
↓
fused bias + activation + dropout
↓
FFN GEMM 2
↓
fused bias + dropout + residual
```

The first fused stage appears because bias, activation, and dropout are all element-wise operations over the same FFN output. The second uses the same postprocessing fusion as attention.

#### C.5 Encoder Orchestrator

[Open `TransformerEncoderLayer::Forward`, lines 255–270](https://github.com/bytedance/lightseq/blob/master/lightseq/csrc/layers/transformer_encoder_layer.cpp#L255-L270)

The top-level forward function is intentionally short.

It:

1. obtains the current CUDA stream and cuBLAS handles;
2. maps the shared workspace to attention/FFN temporary regions;
3. clears mask-related gradient state;
4. runs attention;
5. runs the FFN.

This short function is important conceptually: the C++ layer is an **execution orchestrator**, not one giant CUDA kernel.

### D. Embedding Backward

**Relevant reading:** [Section 2.6](#sec-embedding-backward)

[Open the FP32 embedding-backward kernel, lines 394–458](https://github.com/bytedance/lightseq/blob/master/lightseq/csrc/kernels/cuda/embedding_kernels.cu#L394-L458)

The kernel assigns GPU work according to batch position, sequence position, and embedding dimension.

**Walkthrough:**

1. A thread identifies the token position it is processing.
2. The token id is read from the input sequence.
3. Padding tokens exit early because they should not update the embedding table.
4. The incoming gradient is multiplied by:
   - the embedding scale,
   - the stored dropout mask,
   - the inverted-dropout scale.
5. The token id and feature offset are converted into the destination row/column of the embedding-gradient table.
6. The gradient contribution is accumulated into that location using atomic updates.
7. If quantization metadata is active, related clipping-gradient accumulation is handled as well.

The atomic operation is essential because two positions may contain the same token:

```text
position i ─┐
position j ─┼→ same embedding row
position k ─┘
```

Without atomic accumulation, simultaneous read-modify-write updates could overwrite each other.

The half-precision specialization follows the same logic but vectorizes updates using `__half2`.

<a id="appendix-criterion"></a>
### E. Criterion

**Relevant reading:** [Section 2.7](#sec-criterion)

#### E.1 Forward

[Open the cross-entropy forward kernel, lines 9–62](https://github.com/bytedance/lightseq/blob/master/lightseq/csrc/kernels/cuda/cross_entropy.cu#L9-L62)

The forward kernel combines stable Softmax-related statistics and label smoothing.

**Walkthrough:**

1. One CUDA block handles one token position over the vocabulary dimension.
2. The target id is loaded; padding targets immediately produce zero loss.
3. Threads scan their share of the vocabulary logits and participate in a max reduction.
4. The maximum logit is subtracted before exponentiation for numerical stability.
5. The kernel reduces both:
   - the sum of shifted logits,
   - the sum of exponentials.
6. Thread 0 derives the negative log-likelihood of the target token.
7. Label smoothing mixes target NLL with the vocabulary-wide loss term.

The implementation avoids constructing a separate Softmax tensor and then launching an unrelated criterion kernel. The relevant statistics are computed directly from logits.

#### E.2 Backward

[Open the cross-entropy backward kernel, lines 65–118](https://github.com/bytedance/lightseq/blob/master/lightseq/csrc/kernels/cuda/cross_entropy.cu#L65-L118)

The backward kernel mirrors the paper's simplified gradient.

**Walkthrough:**

1. It recomputes the stable max and exponential sum for the vocabulary row.
2. Each thread derives probabilities for the vocabulary positions it owns.
3. The smoothing contribution is applied to every vocabulary slot.
4. The target slot receives the additional target-specific subtraction.
5. The resulting logit gradient is multiplied by the upstream loss gradient.

The key point is that after the shared Softmax normalization statistics are known, each vocabulary element's final gradient is independent. That is what allows the final gradient stage to parallelize naturally.

### F. Layer-Batched Cross Attention

**Relevant reading:** [Section 2.8](#sec-layer-batched-cross-attention)

[Open `encdec_kv_fw` and backward, lines 214–248](https://github.com/bytedance/lightseq/blob/master/lightseq/csrc/layers/transformer_decoder_layer.cpp#L214-L248)

This function implements the paper's layer-batched encoder K/V projection.

**Forward walkthrough:**

1. Shared K/V memory for encoder-decoder attention is prepared.
2. `_encdec_kv_linear.Forward(...)` receives weights containing K/V projections for **all decoder layers**.
3. Therefore one large GEMM projects the encoder output into a tensor whose feature dimension contains all decoder-layer K/V results.
4. The following bias/layout transform converts:

```text
[batch, src_len, decoder_layers × 2, hidden]
```

into a layout organized by decoder layer, K/V choice, attention head, source position, and head dimension.
5. Each decoder layer later selects its own K and V slice using its layer id.

**Backward walkthrough:**

1. The per-layer K/V gradient layout is transformed back into the large stacked layout.
2. One large linear backward operation computes:
   - gradients for the stacked K/V weights,
   - gradients with respect to the shared encoder output.

This is why the optimization is called **layer-batched**: the GEMM dimension is enlarged by combining work across decoder layers.

<a id="appendix-layernorm"></a>
### G. LayerNorm

**Relevant reading:** [Section 3.2](#sec-layernorm-forward) · [Section 3.3](#sec-layernorm-backward)

#### G.1 Forward

[Open the FP32 LayerNorm kernel, lines 40–84](https://github.com/bytedance/lightseq/blob/master/lightseq/csrc/kernels/cuda/normalize_kernels.cu#L40-L84)

The forward implementation maps directly to the paper's variance rewrite.

**Walkthrough:**

1. Every thread accumulates two local statistics:
   - the sum of \(x\),
   - the sum of \(x^2\).
2. These two values are packed together and reduced by the block in one reduction call.
3. Thread 0 computes:

$$
\mu = E[x]
$$

and

$$
\sigma^2 = E[x^2] - E[x]^2 + \epsilon
$$

4. The reciprocal square root of variance is stored in shared state.
5. Threads synchronize.
6. Each thread normalizes its elements and applies learned scale and bias.

The crucial implementation detail is that `sum(x)` and `sum(x²)` are reduced together. This is the concrete GPU consequence of the algebraic rewrite described in the paper.

#### G.2 Backward

[Open the input-gradient kernel, lines 528–614](https://github.com/bytedance/lightseq/blob/master/lightseq/csrc/kernels/cuda/normalize_kernels.cu#L528-L614)

The backward kernel exposes two shared statistics that correspond to the paper's dependent-reduction discussion.

**Walkthrough:**

1. Each thread computes its local \(dxhat = dout \times \gamma\).
2. It reconstructs \(xhat\) from either:
   - saved input + mean/variance, or
   - output + scale/bias.
3. Two local reduction quantities are accumulated:
   - \(dxhat\),
   - \(dxhat \times xhat\).
4. A single block reduction combines both quantities.
5. Thread 0 converts both totals to means.
6. Every thread computes its final input gradient using the two shared reduced values.
7. If a residual gradient exists, it is added before writing the result.

This is the implementation form of:

```text
one backward formula
↓
extract two global sums
↓
reduce them together
↓
reuse them for every element
```

The half-precision specialization uses the same mathematical structure while converting packed half values to FP32 for sensitive arithmetic.

<a id="appendix-softmax"></a>
### H. Softmax

**Relevant reading:** [Section 3.4](#sec-softmax)

#### H.1 Stable Softmax Kernel

[Open the core Softmax kernel, lines 35–127](https://github.com/bytedance/lightseq/blob/master/lightseq/csrc/kernels/cuda/softmax_kernels.cu#L35-L127)

The implementation follows stable Softmax almost exactly.

**Walkthrough:**

1. Grid coordinates identify the batch item and attention head.
2. A row of attention scores is loaded.
3. Padding or causal masking replaces invalid positions with a large negative value.
4. Every thread finds a local maximum.
5. A block-wide max reduction produces the row maximum.
6. Every valid value is exponentiated after subtracting the maximum.
7. Threads accumulate local exponential sums.
8. A second block-wide reduction produces the denominator.
9. The reciprocal denominator is shared.
10. Threads multiply their exponentials by that reciprocal and write the normalized probabilities.

The two reductions have different roles:

```text
max reduction
→ numerical stability

sum reduction
→ normalization
```

#### H.2 Shape-Dependent Dispatch

[Open the FP32/FP16 dispatch logic, lines 213–278](https://github.com/bytedance/lightseq/blob/master/lightseq/csrc/kernels/cuda/softmax_kernels.cu#L213-L278)

This code makes the paper's shape-aware strategy explicit.

Instead of one fixed launch configuration, LightSeq checks the Softmax length and chooses:

- a small-sequence kernel for very short reductions,
- different block sizes as the sequence grows,
- different grid dimensions for FP32 and FP16.

The reason is hardware utilization. A 32-element reduction and a 1024-element reduction should not reserve the same number of threads or perform the same communication pattern.

#### H.3 Backward Dispatch

[Open Softmax backward, lines 294–368](https://github.com/bytedance/lightseq/blob/master/lightseq/csrc/kernels/cuda/softmax_kernels.cu#L294-L368)

Backward first computes the row-wise dot product between output probabilities and output gradients. Warp shuffles reduce that value efficiently. Each element then applies the standard Softmax Jacobian-vector product using that shared scalar.

The launcher chooses the number of per-thread iterations according to sequence length, again adapting execution to the reduction shape.

<a id="appendix-memory"></a>
### J. Memory Reuse

**Relevant reading:** [Section 5.4](#sec-attention-backward) · [Section 5.5](#sec-preallocation)

#### J.1 Attention-Backward Buffer Aliasing

[Open `attn_layer_bw`, lines 272–374](https://github.com/bytedance/lightseq/blob/master/lightseq/csrc/layers/transformer_encoder_layer.cpp#L272-L374)

The beginning of this function is one of the clearest implementations of dangling-tensor-aware reuse.

Several logical names point into the same shared `buffer`.

For example, the code assigns one region first as an input-gradient temporary and also treats that same starting address as the larger QKV-gradient region. A later region is similarly interpreted as either transformed QKV gradients or Softmax gradients.

The important idea is:

```text
logical tensor name ≠ dedicated physical allocation
```

A pointer name describes **what the region means at the current stage**, not who permanently owns the memory.

**Execution walkthrough:**

1. Residual/postprocessing gradient is computed.
2. Output-projection backward writes a temporary input gradient.
3. That temporary is layout-transformed.
4. Attention-context backward produces:
   - V gradient,
   - Softmax-output gradient.
5. Dropout backward and Softmax backward reuse the Softmax-gradient region.
6. QK backward writes Q and K gradients into the QKV-gradient region.
7. The Q/K/V gradient layout is transformed.
8. QKV projection backward consumes that region and produces the gradient flowing toward LayerNorm/input.
9. Once a stage has consumed a temporary, its storage can be repurposed.

This is the code-level equivalent of the lifetime diagram in Figure 8.

#### J.2 Backward Orchestration

[Open `TransformerEncoderLayer::Backward`, lines 451–473](https://github.com/bytedance/lightseq/blob/master/lightseq/csrc/layers/transformer_encoder_layer.cpp#L451-L473)

The top-level backward function reuses the same shared memory for the FFN and attention phases.

It first gives a region to FFN backward, then reuses the subsequent workspace for attention backward. Comments in the code document the maximum buffer sizes needed by each phase.

This demonstrates the distinction between:

```text
sum of every intermediate tensor size
```

and

```text
maximum memory simultaneously required by the current live set
```

#### J.3 Lifetime of Shared Workspace

[Open the encoder constructor, lines 8–60](https://github.com/bytedance/lightseq/blob/master/lightseq/csrc/layers/transformer_encoder_layer.cpp#L8-L60)

The layer allocates its memory buffer during construction rather than allocating a new set of temporaries for every forward/backward operation. The same shared storage is then sliced and reused throughout execution.

That matches the paper's high-level strategy:

```text
allocate workspace once
↓
reuse it across operators and batches
↓
avoid repeated allocation/free on the hot path
```

[↑ Back to Attention Backward](#sec-attention-backward) · [↑ Back to Preallocation](#sec-preallocation)
